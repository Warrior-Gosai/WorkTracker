# DevWork Tracker — Business Rules

## 1. General Rules

1. The application supports one account only.
2. Business records must be retained for historical reference.
3. Main business records must not be hard-deleted.
4. Business codes are generated by the backend using PostgreSQL sequences.
5. Backend validation is mandatory, even when frontend validation exists.
6. All timestamps must be stored using TIMESTAMPTZ.
7. Application date and time display must use Asia/Kolkata.
8. Project, Task Item and Work Log relationships must follow the approved database design.

## 2. Project Rules

1. Every Project has a unique system-generated Project Code.
2. Project Name is mandatory.
3. Project Name does not need to be unique.
4. Project Start Date and End Date are not required.
5. Project Status:
   - 1 = Active
   - 0 = Inactive
6. New Task Items and Pending Tasks can only be created under active Projects.
7. Existing historical records remain accessible when a Project becomes inactive.
8. Projects cannot be hard-deleted.
9. Project Code cannot be changed after creation.

## 3. Task Item Rules

1. Every Task Item must belong to exactly one Project.
2. Project selection is mandatory.
3. Task Item Code is system-generated and unique.
4. Task Item Title is mandatory.
5. Task Item Title does not need to be unique within a Project.
6. Priority defaults to MEDIUM.
7. Status defaults to OPEN.
8. Is Active defaults to 1.

### Task Item Status

Allowed values:

- OPEN
- IN_PROGRESS
- ON_HOLD
- COMPLETED
- CANCELLED

### Task Item Activation

- 1 = Active
- 0 = Inactive

Activation and workflow status are independent.

A completed Task Item may remain active.

Inactive Task Items cannot be selected when creating new Work Logs.

### Completion Handling

When status changes to COMPLETED:
- Set completed_at to the current timestamp.

When status changes away from COMPLETED:
- Clear completed_at.

When status remains COMPLETED:
- Preserve the existing completed_at value.

Task Items cannot be hard-deleted.

## 4. Work Log Rules

### 4.1 Relationships

1. Every Work Log belongs to exactly one Task Item.
2. Every Task Item belongs to one Project.
3. Project information is derived through the Task Item.
4. Project ID must not be stored redundantly in Work Log.
5. A Work Log can have zero or multiple Code Changes.
6. A Work Log can have zero or multiple DB Changes.
7. Multiple Work Logs can exist on the same date.
8. Each Work Log represents one Task Item only.

### 4.2 Creation Validation

- Task Item is mandatory.
- Task Item must exist.
- Task Item must be active.
- Work Date defaults to the current date.
- Environment defaults to LOCAL.
- Work Type is mandatory.
- Task Requirement is mandatory.
- Status is mandatory and defaults to IN_PROGRESS.

### 4.3 Work Log Status

Allowed values:

- COMPLETED
- IN_PROGRESS
- BLOCKED
- ON_HOLD

Default: IN_PROGRESS.

Work Log Status is independent of Task Item Status.

Changing a Work Log status must not automatically change the Task Item status.

### 4.4 Environment

Allowed values:

- LOCAL
- UAT
- LIVE

Default: LOCAL.

Each Work Log has one primary environment.

Code Changes and DB Changes can have their own environments.

### 4.5 Time Tracking

1. Start Time defaults to 09:00 AM in the frontend.
2. End Time is initially empty.
3. Both fields are optional.
4. Both fields can be cleared together.
5. Both populated: calculate duration.
6. Both empty: save without duration.
7. Only one populated: validation error.
8. Overnight duration is supported when End Time is earlier than Start Time.
9. Identical times are treated as zero duration.
10. Total Hours is calculated by the backend.
11. Total Hours must not be independently stored in the database.

### 4.6 Work Log History

- Work Logs must remain accessible even when their Task Item or Project becomes inactive.
- Work Logs cannot be hard-deleted.
- Updating a Work Log must not create a duplicate record.
- Associated Code Changes and DB Changes must remain linked to the original Work Log.

## 5. Pending Task Rules

### 5.1 Relationships

1. Every Pending Task belongs directly to one Project.
2. Project ID is mandatory.
3. Pending Tasks are independent of Task Items.
4. Pending Tasks are independent of Work Logs.
5. No Task Item ID or Work Log ID relationship is allowed.

### 5.2 Creation

- Project must exist and be active.
- Title is mandatory.
- Priority defaults to MEDIUM.
- Status defaults to PENDING.
- Due Date is optional.
- Pending Task Code is system-generated.

### 5.3 Status

Allowed values:

- PENDING
- IN_PROGRESS
- ON_HOLD
- COMPLETED
- CANCELLED

### 5.4 Completion

When status changes to COMPLETED:
- Set completed_at to the current timestamp.

When status changes away from COMPLETED:
- Clear completed_at.

When status remains COMPLETED:
- Preserve the existing completed_at.

### 5.5 Overdue Calculation

A Pending Task is overdue when:

- due_date is earlier than the current date; and
- status is neither COMPLETED nor CANCELLED.

A task due today is not overdue.

Overdue status is calculated dynamically. It is not stored as a separate database status.

Pending Tasks cannot be hard-deleted.

## 6. Code Change Rules

### 6.1 Relationships

1. Every Code Change belongs to exactly one Work Log.
2. A Work Log can have multiple Code Changes.
3. Each Code Change can contain zero or multiple Code Change File records.
4. Project and Task Item information are derived through the Work Log relationship.

### 6.2 Change Status

Allowed values:

- COMMITTED
- UNCOMMITTED

### 6.3 COMMITTED Records

- SVN Commit ID is mandatory.
- SVN Commit ID must be unique.
- Actual commit date/time is mandatory.
- Environment is mandatory.
- File details are optional.

### 6.4 UNCOMMITTED Records

- SVN Commit ID must be NULL.
- Change date/time is mandatory.
- Environment is mandatory.
- File details are optional.

### 6.5 Conversion

When an UNCOMMITTED Code Change becomes COMMITTED:

1. Update the existing Code Change.
2. Add SVN Commit ID.
3. Record actual commit date/time.
4. Change status to COMMITTED.
5. Retain existing file details.
6. Do not create a duplicate Code Change.

### 6.6 File Details

- File Path is mandatory when a file detail row exists.
- Layer, Technology, What Changed, Why Changed, Affected Files and Remarks are optional.
- File details may be added or updated independently.
- Optional file detail rows can be deleted.
- Deleting a file detail must not delete the parent Code Change.

### 6.7 Commit Relationship

- One SVN commit represents one Code Change.
- Multiple files can belong to one commit.
- Multiple commits require separate Code Change records.
- SVN integration is not supported.
- SVN information is entered manually.

## 7. Database Change Rules

### 7.1 Relationships

1. Every DB Change belongs to exactly one Work Log.
2. One Work Log can contain multiple DB Changes.
3. Project and Task Item information are derived through Work Log relationships.

### 7.2 Mandatory Fields

- Work Log
- Environment
- Database
- Object Type
- Object Name

### 7.3 Environment

- LOCAL
- UAT
- LIVE

### 7.4 Database

- Oracle
- PostgreSQL
- MySQL
- SQL Server
- MongoDB
- Other

### 7.5 Object Type

- Table
- Procedure
- Function
- Trigger
- View
- Package
- Cursor
- Sequence
- Index
- Constraint
- Other

### 7.6 Record Handling

- One DB Change record represents one database object change.
- Multiple object changes require multiple records.
- Affected Object can contain multiple affected object names.
- DB Change Code is system-generated.
- DB Changes cannot be hard-deleted.

## 8. Authentication Rules

1. Only one account can exist.
2. Registration is available through the hidden setup route only.
3. Registration is enabled only when no account exists.
4. Backend must enforce the single-account restriction.
5. Registration must be protected against concurrent first-account creation.
6. Passwords must be hashed using BCrypt.
7. Login accepts username or email.
8. Access tokens are short-lived JWTs.
9. Refresh tokens are opaque random tokens.
10. Refresh tokens are stored as SHA-256 hashes in the database.
11. Refresh-token rotation is mandatory.
12. Logout revokes the refresh token.
13. Reuse of an old refresh token triggers token-family revocation.
14. Inactive accounts cannot log in or refresh tokens.
15. Account status must be checked on every authenticated API request.
16. No password recovery or email verification initially.

## 9. Business Code Generation

All business codes are generated by the backend using PostgreSQL sequences.

| Entity | Format |
|---|---|
| Project | PRJ-000001 |
| Task Item | TASK-000001 |
| Work Log | WL-000001 |
| Code Change | CC-000001 |
| DB Change | DB-000001 |
| Pending Task | PT-000001 |

Rules:

- Never generate codes using MAX(id) + 1.
- Sequence gaps are acceptable.
- Codes are immutable after creation.
- Codes must be unique.

## 10. Timestamp Rules

1. created_at is assigned when a record is created.
2. updated_at changes when an existing record is updated.
3. Timestamps are stored as TIMESTAMPTZ.
4. Display and input conversion use Asia/Kolkata.
5. completed_at is managed by backend business logic.
6. The database timestamp trigger manages updated_at for applicable tables.

## 11. Historical Data and Deletion

Main business records must not be hard-deleted:

- Project
- Task Item
- Work Log
- Pending Task
- Code Change
- DB Change

Use status or activation controls where applicable.

Optional Code Change File records may be deleted without deleting their parent Code Change.

Foreign keys must protect historical relationships.

## 12. Excel Export Rules

### Daily Work Log
- Preserve the existing 22-column mapping.
- Derive Project and Module/Feature through Task Item.
- Calculate Day from Work Date.
- Calculate Total Hours.
- Derive Code Change IDs and DB Change IDs from relationships.

### DB Change Log
- Preserve all original 12 columns.

### Code Change Log
- Preserve original 11 columns.
- Add SVN Commit ID and Change Status.
- Export one row per Code Change.
- Aggregate multiple file details into newline-separated cells.
- Do not duplicate parent records for multiple files.

Use the original workbook templates during implementation.

## 13. Validation and Error Handling

- Validate all required fields.
- Validate allowed enum values.
- Validate referenced records.
- Validate active Project and Task Item restrictions.
- Validate unique business codes and SVN Commit IDs.
- Return consistent API error responses.
- Use HTTP 409 for business conflicts where appropriate.
- Never expose database stack traces or secrets to clients.
